# Design review 0005

Written after cycles 1-4 (AP-0001 abandoned, then AP-0002, AP-0003 and AP-0004 merged). It covers the
places where the design makes change hard or risky, and ends with three proposals for the backlog. No code
was changed in this stage.

## What the last four cycles show

| Cycle | Requirement | What went wrong, or cost an attempt |
|---|---|---|
| 1 | AP-0001 vSphere contract | 3 attempts, abandoned. Each one failed on staging because `Map<String,Object>` on `/vsphere/status` was documented as `additionalProperties: {type: object}`. `mvn test` passed every time. |
| 2 | AP-0002 (retry) | Passed first time, but only because the backlog item spelled out the fix. |
| 3 | AP-0003 409 on finished requests | Attempt 1 failed on staging: a request reaches CANCELLED before its workflow closes, and a signal sent in that gap is accepted and ignored. The fix (`requireNotFinished`) is a check-then-signal and still has a race. |
| 4 | AP-0004 catalog contract | The same `Map<String,Object>` bug again, this time on `/classifications`. The developer couldn't run the contract test locally, so drift could only show up on staging. |

So three of the four requirements were about one thing: the OpenAPI document didn't match what the server
actually sends. The only place that mismatch can be caught is a staging run, which is the slowest and most
expensive step in a cycle.

## Where the design makes change hard or risky

1. **Old acceptance tests block legitimate future changes.** `runChecks`
   (`agent-pipeline/src/activities.ts:345`) runs every acceptance test against every cycle's branch, and
   the developer may not edit `tests/acceptance/**`. Two tests in
   `tests/acceptance/ap-0004/docs_and_repo.test.mjs:192-208` diff `merge-base(HEAD, main)...HEAD`. They fail
   if the branch touches anything under `workflow/`, `security/`, `resources/catalog/`, `application*.yml`,
   any file named `*Auth*` or `*Security*`, or adds a `@SignalMethod`/`@UpdateMethod`. On `main` that diff
   is empty, so the live check passes. **On any future cycle branch that changes a workflow, they fail, and
   no agent is allowed to fix them.** These tests were meant to say "AP-0004 didn't touch X". As written,
   they say "nobody may ever touch X". `ap-0003` got the scoping right: it only looks at commits whose subject
   contains `AP-0003` (`ap-0003/docs_and_repo.test.mjs:161`). This is a latent deadlock, and it is the most
   urgent item here.

2. **The response type and the OpenAPI document are only compared at runtime, on staging.** springdoc turns
   a `Map<String,Object>` or `ResponseEntity<?>` return into a schema that doesn't match the real JSON, and
   nothing in `mvn test` notices. One such endpoint is still left:
   `VsphereController.blueprint()` (`VsphereController.java:114`) returns `Map<String,Object>`. The contract
   test never sees its 200 response, because staging has no VCF Automation, so this one will only fail on a
   real installation. `BatchController` and `legacyCreate` return `ResponseEntity<?>` and rely on
   hand-written `@ApiResponse` annotations staying correct.

3. **The OpenAPI snapshots are generated by hand, and the build doesn't check them.** Three acceptance test
   files (`ap-0002`, `ap-0003`, `ap-0004`) each assert that `docs/openapi.json` equals the live document
   exactly. So every API change has to regenerate the snapshot, or three older tests fail. But no unit test
   compares them, and no build command writes them. Each requirement still says "mvn test passes, including
   any test that compares the snapshots": no such test exists.

4. **The same counts are maintained by hand in many places.** One API change means editing
   `docs/API.md` ("It runs 55 checks", "all 42 operations"), the contract test, and two snapshots. Those
   counts are then checked by three different rules: a regex in `ap-0003`, a different regex in `ap-0004`,
   and the script's own runtime count in `ap-0004/contract_run`. A check written in a loop, or a `call(`
   split across lines, would make the three rules disagree.

5. **The contract test runs twice per staging check.** It runs once as the pipeline check `API contract
   (OpenAPI)` (15-minute timeout), and again inside `ap-0004/contract_run.test.mjs`, which the pipeline runs
   with a 10-minute acceptance timeout. That roughly doubles the VMs built and the staging time. It also adds
   a chance of a spurious timeout as the script grows.

6. **Request changes that come in as signals are checked first, then sent.** Clarify and cancel are
   signals, so the workflow can't refuse them. The controller first asks the workflow for its state, then
   sends the signal (`RequestController.requireNotFinished`, `:347`). A request that finishes between those
   two calls still gets a 204 for a change that is silently dropped. Cancel during PROVISIONING also returns
   204 and does nothing (its documentation says "Has no effect once the build has started"). `confirmSpec`
   already does this properly, as an update with a validator, and `ApiErrorHandler.updateRefused` already
   maps a refused update to 409.

7. Smaller points:
   - HTTP status mapping is spread around: `VsphereController.statusFor`,
     `RequestController.finishedOr404`, CatalogController's "already ended", and many ad-hoc
     `ResponseStatusException`s. Workable for now; it's a candidate once proposal 2 makes drift visible.
   - `ap-0002/vsphere_docs_and_repo.test.mjs:199` greps test source code for `SERVICE_UNAVAILABLE ...
     NOT_SET_UP`, which ties future refactors to today's spelling.

## Proposals

### 1. Scope "must not change" acceptance checks to their own requirement (low risk; needs a person)

Rewrite the two criterion-8 tests in `tests/acceptance/ap-0004/docs_and_repo.test.mjs` the way `ap-0003`
does it: look at the files changed by commits whose subject starts with `AP-0004:`
(`git log --format=%H --grep '^AP-0004:'` and then `git show --name-only` on each, plus uncommitted
changes), not the whole branch diff against main. Then the check stays true for AP-0004 and stops blocking
later cycles. It is about 15 lines.

**Who can build it:** the developer may not edit acceptance tests, and `agent-pipeline/**` is protected,
so a person should make this edit. Or a person could allow the tester to edit older acceptance folders when
a requirement explicitly asks for it. As a lasting rule for the requirements agent and the tester: phrase a
"must not change" criterion as "no commit for this requirement touches X", never as "the branch doesn't
touch X".

It must be done before proposal 3, which changes `IntentWorkflow` and would otherwise fail AP-0004's
acceptance test on staging.

### 2. Check the OpenAPI document in `mvn test`, and write the snapshots from it (medium risk; 1-2 cycles)

Move the drift check from staging into the build:

- Add `backend/src/test/java/.../api/OpenApiDocumentTest.java`. It starts a slim web context
  (`@WebMvcTest` for the `api` controllers, mocked collaborators, springdoc, `OpenApiConfig` and
  `SecurityOpenApi`) and fetches `/v3/api-docs`. It then:
  - (a) fails if any 2xx response schema is a free-form map (`additionalProperties: {type: object}`) or an
    untyped `object`. Allow a short explicit list of exceptions, for example where API.md's "free-form
    values" convention applies.
  - (b) compares the document (without `servers`) with `docs/openapi.json` and `docs/openapi.yaml`, and
    rewrites both when run with `-Dopenapi.write=true`. The developer's allowed `mvn` command can run that.
- Fix what (a) finds. At least: give `getVsphereBlueprint` a named response record, for example
  `VsphereBlueprintResponse(blueprint, releasedVersions, inputs)` with `inputs` free-form, without changing
  the JSON.
- `docs/API.md`, "Checking the contract": add one line on how to regenerate the snapshots.

Acceptance can be checked on staging: the live `/v3/api-docs` still equals `docs/openapi.json`. The
`getVsphereBlueprint` 200 response refers to a named schema. `mvn test` contains the new test. The test
fails when a snapshot is edited by hand (the tester can check this with a modified copy).

Risks: the slim context may produce a slightly different document from the full application (security
schemes depend on `VMINTENT_SECURITY_MODE`; staging uses `none`). If it does, a `@SpringBootTest` that mocks
the Temporal client and turns off the embedded database is the fallback. If the context work grows, split
it: cycle A covers (a) and the blueprint type, cycle B covers (b).

### 3. Make clarify and cancel Temporal updates with validators (medium risk; 1 cycle; after proposal 1)

Add `@UpdateMethod`s `answerQuestion(String answer)` and `cancelRequest()` to `IntentWorkflow`, each with an
`@UpdateValidatorMethod`:

- `answerQuestion` is refused unless the state is `AWAITING_CLARIFICATION`.
- `cancelRequest` is refused unless the request is still waiting (clarification or confirmation).

Each handler sets the same fields as the existing signal, so the workflow's sequence of commands doesn't
change. Keep the old `clarify`/`cancel` signals so that running workflows and the recorded histories
(`intent-v1-*.json`) still replay. `RequestController.clarify`/`cancel` call the updates and drop
`requireNotFinished`. A refused update becomes 409 through the existing `ApiErrorHandler.updateRefused`.
`finishedOr404` stays for closed workflows.

This removes the race from item 6, so a 204 always means the change took effect. It also replaces the
silent no-op with a clear 409 ("the build has already started") when someone cancels during PROVISIONING.
That is a visible behaviour change: document it in the `cancelRequest` row and `@ApiResponse` of API.md,
and check the Cancel buttons in `frontend/src/App.tsx` show the message. Add a replay history recorded with
the update path. Unit tests cover both validators. The AP-0003 behaviour (409 on finished, 404 on unknown,
204 on the happy paths) must stay as it is.
